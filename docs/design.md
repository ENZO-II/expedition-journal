# 设计与实施路线

此文档是建议方案，不代表功能已实现或用户已逐项确认所有技术细节。

## 产品结构

一个应用容纳多个战役。战役有自己的访问地址与邀请关系，无须为每个团复制网站。

建议实体关系：Campaign → Membership → Character；Campaign → Map → Marker；Campaign → JournalEntry；Character → Inventory；Campaign → SharedInventory。

JournalEntry 分别保存 authorMemberId、characterId、createdAt、updatedAt、稳定写入序号，以及可选的冒险日期与排序键。角色姓名变化不能改变条目所有权。冒险历法不能硬编码为公历 Date。

Owlbear 房间绑定战役；地图标注与场景关联只是入口，长期数据独立保存。Owlbear SDK 给出的玩家 ID 不能未经服务端验证就被当作独立服务的登录凭据。

## 主要交互

1. 主持人建立战役，邀请成员。
2. 玩家输入角色姓名，登记角色；以后可以添加和切换角色。
3. 地图上选点放置标注，展开日记编辑面板，写入并自动保存。
4. 从地图或手记列表阅读同一篇日记，按冒险时间或写入顺序排列。
5. 角色创建文本物品，存入公库或转交其他角色。
6. 导出可阅读的冒险记录和可恢复的数据备份。

## 页面行为

- 地图工作状态：主要区域是地图，右侧展开日记，保留地点上下文。
- 专注阅读状态：空间足够时显示跨页；窄屏采用单页。
- 图标与彩饰不替代清楚的操作文字。可触摸目标、键盘焦点、文字放大和中文阅读要一起验证。
- 真实手抄本素材应有固定尺寸策略，避免正文变化时拉伸变形。

## 数据实施要求

- 服务端按战役与成员验证访问，不以隐藏按钮替代权限检查。
- 成员、角色和现实作者分别建模；角色注册不等于账户注册。
- 多人共享内容需要持久化服务，不能把 localStorage 当共享数据库。
- 自动保存要处理失败和版本冲突；不能显示已保存而实际丢失。
- 公库转移使用事务或等价的原子操作，同时减少来源、增加目标；重试不重复领取。
- 上传文件与私有数据保存在运行时存储，公开代码仓库不承担数据库职责。
- 恢复机制与可迁移备份随核心功能一起实施。

## 分阶段验收

1. **交互样稿**：电脑与平板的地图标注、日记展开、角色登记/切换、背包公库入口；演示内容明确标注。
2. **多人基础**：战役隔离、邀请与成员识别、角色归属、跨设备接续、持久化。
3. **完整流程**：地图导入、标记、日记双排序、物品原子转移、恢复与导出。
4. **Owlbear 接入**：在真实房间验证入口与地图关联、切场景、重连、不同玩家权限。
5. **公开试用**：安装/部署指南、空白战役流程、素材清单及真实设备验证。

不能把第 1 阶段的静态或本机样稿描述成已经支持多人在线的完整产品。
